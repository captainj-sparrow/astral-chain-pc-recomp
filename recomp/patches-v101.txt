# Scene size for the upscaling modes (runtime/resolution.c scene_init: upscaling_quality quality, balanced, performance
# or ultra_performance with an upscaler able to run at start). The game keeps three dynamic-resolution levels, each with
# its own scene targets (light target, scene depth and the passes sized from them), made by the function at 40fb60
# (level, width, height); the per-frame selector at 4183a0 points the renderer at one level's targets, and the output
# and HUD stay at the render size (4328c0, which res / res1062 set). These six csel pick each level's width (w1) and
# height (w2) from the docked or handheld values; the helpers load the scene size from the patch page (+16, {w, h} as
# floats) instead, for both modes and every level, so the level the game picks no longer matters. The cmp before them

# prepass, the light target, the bloom and the composite all follow, and the SMAA blending pass draws the composite into
# the output, the game's only scaling pass, where runtime/vk_dlaa.c runs the upscaler. Off unless the scene is smaller
# than the game resolution: without an upscaler the game's plain scaling would show it at 33..67 % of the output. Read
# at start; the game makes its scene targets once, so a change waits for a restart.

# The game resolution (runtime/resolution.c res_pick, AC_OUTPUT_RES): the res1062 sites, each taking the output size
# from the patch page (+32: width, +36: height, u32) instead of a constant, so any size runs without a set of its own,
# as the TotK Recomp's output set does. 1920x1080 by default, as 1.0.0's res1080 set, the ladder's docked entries
# included, so the scene stays at the output size whatever scale the dynamic-resolution logic picks. Only 16:9 sizes of
# 32n x 18n are taken (resolution.c res_size): 1280x800 lost the device, and in handheld took the docked entries below.
# Each ladder level picks one size when the scene target has the docked width and another when it has not; handheld
# (1280x720 targets, main+0x40d5a0) always takes the second. Those two handheld entries (40f1a4 and 40f1b0) get
# res1062's 1280x720, the handheld targets' own size: a larger size there is larger than the targets the game made for
# handheld, the level's target is never created, and loading a save in handheld read through its null texture in
# main+0x9d0df0 (issues #25 and #38). Level 2's docked width is w19, which the function sets to the handheld 1280 before
# the ladder (main+0x40f128, also the width of a 1280x720 target it makes there, so left alone): with the height raised
# to 1080 that level was 1280x1080, and the former AC_SSAA=1440p made it 1707x1440, which lost the device on an RTX 5070
# Ti (issue #51). 40f1d8 takes the scene target's width (w0) instead, as level 0 does, so the level has the output size
# docked and keeps 800x720 in handheld. res1062 gets the same site.
# Above 1080p the render size alone (0x4328c0) breaks start-up: the game's render targets and its three window textures
# (main+0x9e8620; general textures through main+0x9ead20) come out of one budget the graphics configuration sets at
# main+0x40e0b0 (+0x88: 0x13600000, 310 MiB), carved from the process heap. At 1080p its 81 allocations take 304 MiB;
# at 1440p one fails, the device setup gives up quietly, and start-up crashes reading a list it never filled
# (main+0x9c0cd0). So the budget follows the output's pixel count (rt_res_budget_w8; measured over 75 s into play:
# 1440p took 482 MiB, 2160p 955 MiB, the same 81 allocations), and the process heap grows by the same amount
# (resolution.c res_heap_extra_bytes; without it the game prints NN_MEMORY_INFO with the shortfall).

# Dynamic frame rate for the 60 fps mode (the menu's AC_FPS: 30 = shipping 30 fps, 60 = 60 fps with the fix).
# The game's frame timer (main+0x91DBB0) clamps its step to [1, 2] frames of 1/30 s, so at 60 fps everything runs at
# twice its speed. The set replaces the timer's step with the frame's real time (runtime/frame_rate.c rt_fps_timer,
# which also keeps the whole 30 fps ticks the steps add up to), and fixes what counts frames instead of reading the
# step: every input/action/hitstop/rumble frame counter is scaled by the whole ticks so its window lasts wall-clock time

# full-screen movie is held to 30 presents per second (frame_rate.c cutscene_rate) and steps by the whole 30 fps
# frames of the real time (frame_rate.c held_step). Sites from the
# AstralChain-Dynamic-FPS mod v1.1.1 are marked so. AC_FPS=30 runs the original instructions (the shipping 30 fps).
